页面无法正常连接，WebSocket 断开。

问题分析

错误原因

OpenClaw 是一个实时聊天应用，依赖 WebSocket 长连接。工作流程如下：

  1. 浏览器访问根路径 /，加载 HTML 页面
  2. 页面中的 JavaScript 代码立即建立 WebSocket 连接到 /
  3. 我的配置对所有访问 / 的请求都做了 301 重定向
  4. WebSocket 握手请求也被重定向到了 /chat?...
  5. WebSocket 连接失败 → 错误码 1006（异常断开）

核心问题

没有区分普通 HTTP 请求和 WebSocket 请求，一刀切的重定向导致 WebSocket 无法建立连接。

正确的修复方案

第一步：在 nginx.conf 中添加 WebSocket 检测

在 http 块中添加以下 map 指令：

  • $http_upgrade：HTTP 请求头中的 Upgrade 字段
  • WebSocket 握手时，该字段值为 websocket
  • 普通请求时，该字段为空或其他值

第二步：修改 openclaw.conf

关键点

  1. 使用 if ($is_ws = 0) 判断是否为普通 HTTP 请求
  2. 只有非 WebSocket 请求才执行重定向
  3. WebSocket 请求正常代理到后端网关
  4. 使用 302 而非 301，避免浏览器缓存重定向规则

我的反思

错误原因总结

问题 说明
没考虑 WebSocket OpenClaw 是实时聊天应用，依赖 WebSocket 长连接
一刀切重定向 对所有 / 请求无差别重定向，包括 API 和 WebSocket
缺乏场景分析 应该区分”人类访问页面”和”程序建立连接”

教训

配置涉及 WebSocket 的服务时，必须：

  1. 识别 WebSocket 请求（通过 $http_upgrade 头）
  2. 只对普通 HTTP 请求做重定向
  3. WebSocket 连接必须原样代理到后端

正确的思考方式

在修改 nginx 配置前，应该问自己：

  • 这个服务使用什么协议？（HTTP/HTTPS/WebSocket）
  • 有哪些类型的请求会访问这个路径？
  • 重定向会影响哪些请求？
  • 是否有特殊请求需要例外处理？

最终效果

修复后：

  • ✅ 访问 https://openclaw.iambeyouare.com/ → 浏览器自动跳转到聊天页面
  • ✅ WebSocket 连接正常建立 → 实时消息功能正常
  • ✅ 其他路径正常代理 → API、静态资源等均不受影响
